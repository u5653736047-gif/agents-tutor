# FTS5 候选预筛性能基准（S5-C4 验收证据）

- 日期：2026-08-23
- 环境：Windows 11 / Python 3.11（SQLite 3.45.1，FTS5 可用）
- 语料：15,000 chunks 合成语料——每条含 25 个公共领域词（低选择性填充）+
  唯一字母数字 token（`xref{hex}`，高选择性词项）；随机种子 42
- 查询负载：高选择性（唯一 token 精确检索，候选 5/15000 ≈ 0.03%）与
  低选择性（多字中文词组合，单字词项全库命中，候选 ≈ 100%）两类

## 结果（5 轮均值，5 查询/轮）

| 场景 | 全表扫描 | FTS 路由后 | 加速比 |
| --- | --- | --- | --- |
| 高选择性 token 查询 | 1711.8ms | **0.35ms** | **≈4938x** |
| 低选择性中文查询 | 972.6ms | 1003.8ms | 0.97x（回退 + COUNT 探测开销 ≈3%） |

## 等价性验证

两路径对同批查询返回的 chunk_id 序列与分数（6 位小数）逐项一致 ✓；
专项测试见 `tests/test_knowledge_fts.py`（过滤/排除/top_k/超限回退/空词项）。

## 结论与机制说明

1. **高选择性查询收益巨大**：MATCH 只走 FTS 索引圈定极小候选集，
   Python 打分从 O(全库) 降为 O(候选)。
2. **低选择性查询自动零损失回退**：典型中文多字查询的单字词项天然
   全库命中（本批次实测候选占比 100%），物化全部候选再打分并不比
   全表扫描便宜。因此路由层先做毫秒级 COUNT 探测，候选数超过
   `_FTS_CANDIDATE_LIMIT`(2000) 即回退全表扫描——开销仅为一次 COUNT。
   该路由不改变任何返回结果（两条路径结果集相同，测试锁定）。
3. **诚实的适用边界**：本方案的价值在「精确词项可区分」的查询
   （编号、专名、英文术语）；对纯中文短查询的提速受打分模型的
   单字命中语义约束（计划边界明确不改打分语义）。若未来需要中文
   查询也获得剪枝收益，需调整打分模型本身（超出本批次边界）。

## 复现方式

随仓库提交的脚本：`backend/scripts/bench_fts.py`（语料规模 / 随机种子 /
查询负载参数化，输出本报告同构的 markdown 表格）。

```bash
cd backend && .venv/Scripts/python.exe scripts/bench_fts.py --chunks 15000
```

路由开关为 `SqliteKnowledgeIndex._fts_enabled`（True=FTS 路由，False=全表扫描），
脚本内部自动切换两路对比。
